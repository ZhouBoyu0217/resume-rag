# 简历知识库问答系统

一个基于 RAG（检索增强生成）的简历分析与问答系统。上传简历后，可以用自然语言询问简历内容，回答附带原文依据；也支持跨简历横向比较、按岗位 JD 做匹配打分。

> 个人学习实践项目，目标是把 RAG 从切分、向量化、检索、生成到部署的完整链路跑通，并验证每一步的设计取舍。

---

## 这个项目解决什么问题

用大模型直接问简历有两个绕不开的问题：**它不知道你的简历内容**，而且**它会编**。

RAG 的思路是把简历先变成可检索的知识库：提问时先检索出最相关的几段原文，再连同问题一起交给大模型，让它只依据这些内容作答。这样既解决了"模型不知道"，也让答案可以回溯到具体出处。

具体到这个项目：

- 简历里有很多份候选人的信息，需要按人区分、按人提问，不能串味
- 回答必须能指回原文，否则无法验证真假
- "这批人谁最适合这个岗位"这类全局问题，靠单条检索答不了，需要另一套机制

## 系统架构

```
上传简历 (.txt)
    │
    ├─→ chunk_text()      按 [章节] 聚合切块，超长块重叠切分
    │        │
    │        ├─→ embed()          bge-m3 向量化
    │        │        │
    │        │        └─→ Chroma  存向量 + 元数据（resume_id / resume_name）
    │        │
    │        └─→ storage/          原文归档（双写）
    │
提问
    │
    ├─→ embed(question)   同一模型向量化，保证同一坐标系
    │
    ├─→ Chroma.query()    top_k 相似块，可选 where 过滤 resume_id
    │
    └─→ DeepSeek 生成      只依据检索到的原文作答
             │
             └─→ SSE 流式返回（sources → delta → done）
```

**两条独立的检索路径**，对应两类问题：

| 问题类型 | 走哪条路 | 原理 |
|---|---|---|
| "陈宇做过哪些项目" | 向量检索（top_k=6） | 问题向量找最相似的原文块 |
| "这批人谁 RAG 经验最扎实" | 摘要层（Map-Reduce） | 每份简历压成摘要，全部摘要一起交给模型比较 |

## 技术栈与选型理由

| 层 | 选择 | 为什么不用别的 |
|---|---|---|
| Web 框架 | FastAPI | 类型标注自动解析参数与校验；原生支持 `StreamingResponse` 做流式；自动生成 `/docs` |
| 向量库 | Chroma | 纯本地持久化，无需起服务；支持 metadata 过滤，够这个数据量用。数据上万条会考虑 Milvus |
| Embedding | bge-m3（硅基流动 API） | 中文效果好、支持长文本、无需自己部署模型 |
| 生成模型 | DeepSeek | OpenAI 兼容协议，切换成本低；中文表现稳定 |
| 前端 | 原生 HTML/CSS/JS 单文件 | 项目规模不需要框架；面试时能现场改；部署只需一个文件 |

**为什么用 RAG 而不是微调？** 简历会不断新增和修改，RAG 更新知识库只需重新入库，微调则要重新训练。而且微调无法给出"依据出自原文哪里"，可解释性差。

## 核心接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/upload` | 上传简历，切分 + 向量化 + 原文归档 |
| GET | `/resumes` | 列出所有简历 |
| GET | `/resumes/{id}/text` | 取原文（抽屉"全文"页） |
| GET | `/resumes/{id}/summary` | 生成/读取摘要（带缓存） |

## 设计要点

### 1. 切分：为什么不按换行切

最早的版本按换行切分，出了个典型问题：问"有哪些项目经历"，系统回答"简历里没有提到"。

原因是 `[项目经历]` 这个标题被单独切成了一块只有 6 个字的内容，而标题下面的正文散落在别的块里。检索时命中了这个空标题块，模型看到的上下文里没有实际内容。

现在的策略分三层：

1. **按 `[章节]` 聚合**——标题和它下面的内容合成一块，标题不再孤立
2. **标题回填**——每块开头补上所属章节名，让向量带上"这段属于工作经历还是项目经历"的语义线索
3. **重叠切分**——超长块按 500 字硬切，相邻块重叠 80 字，避免句子被边界拦腰截断

代价是：同一章节切出的多块开头都带有相同标题，检索时可能占满 top_k、挤掉其他章节。这个问题可以用 MMR（最大边际相关性）重排缓解，当前版本没有做。

### 2. 双写：索引和原文分开存

Chroma 存的是**切分后的块**，不是完整简历。原文单独存在 `storage/{resume_id}.txt`。

必须分开的原因：

- 向量库的块之间有重叠，拼接回去会有重复文本
- 改切分策略时，只有原文才能重新切
- 下载功能需要完整原文

### 3. 身份识别：用 id，不用名字

`resume_id` 是时间戳 + 文件名生成的唯一标识，`resume_name` 只做展示。

同名简历上传时返回 409 拒绝，而不是静默覆盖——现实中同名不同人是常态，覆盖会丢数据。409（Conflict）在语义上表示"请求和资源当前状态冲突"，比 400 或 500 更准确：请求本身格式没问题，是服务器上已存在冲突的资源。

### 4. 流式输出：先给依据，再给正文

`/chat/stream` 用 SSE 推送三种事件：

```
event: sources   → 检索到的原文块（含距离、简历名）
event: delta     → 增量文字，多次
event: done      → 结束
```

**先发 sources 再发正文**，是因为检索在生成之前就完成了。前端可以在第一个字出现之前就把引用卡片画出来，用户立刻能看到"系统找到了什么依据"，而不是干等十几秒。

前端同时实现了降级：SSE 失败且尚未吐出内容时，自动回落到 `/chat` 一次性获取 + 前端逐字显示（typewriter）。流式已开始超过 1.5 秒才断的，不降级，避免答案重复两遍。

### 5. 元数据过滤：多份简历不串味

`/chat` 接受可选的 `resume_id` 参数，非空时检索加上 `where={"resume_id": ...}`，只在这份简历的块里找。

没有单独建多个 collection，因为 Chroma 的 metadata 过滤在底层就是索引条件下的检索，同一个集合按字段过滤即可，省去管理多个集合的复杂度。

### 6. 全局问题：RAG 解决不了的部分

"这几份简历有什么共同点"这类问题，靠 top_k 检索天然覆盖不全——只能捞到几块，看不到全貌。

解法是 Map-Reduce：每份简历离线压成 150-260 字摘要，提问时把所有摘要一起喂给模型。摘要缓存在 `storage/summaries/`，避免每次重新生成。

## 踩过的坑

| 问题 | 根因 | 解决 |
|---|---|---|
| 问项目经历答"没提到" | 按换行切分，标题成孤立空块 | 改为按章节聚合 + 标题回填 + 重叠切分 |
| `/resumes` 返回 500 | 早期 `build_db.py` 建的块没有 metadata，遍历时 `None.get()` 崩溃 | 统一过滤 `None` 元数据；`/health` 加兜底永不崩 |
| 简历文件名变成 `xxx.txt.txt` | `resume_id` 用完整文件名拼接，又加了一次扩展名 | 先 `os.path.splitext` 去掉扩展名 |
| 长回答滚不到底部 | flex 子项缺 `min-height: 0`，被内容撑高溢出容器 | 滚动容器加 `min-height: 0`，grid 改 `minmax(0, 1fr)` |
| 流式渲染露出 `**` 星号 | 边流边渲染 Markdown，标记未闭合 | 流式阶段显示纯文本，结束后统一渲染 |
| 跨简历分析像卡住 | 首次分析需逐份生成摘要，耗时累积 | 前端显示已等待秒数 + 说明首次较慢 |

## 目录结构

```
resume-rag/
├── main.py            FastAPI 应用：路由注册、请求校验、响应组装
├── rag_core.py        核心能力：切分、向量化、建库、原文归档、删除
├── query.py           检索 + 生成：retrieve / answer / stream_answer
├── summary_core.py    摘要层：跨简历的 Map-Reduce
├── analyzer.py        单份简历分析：摘要、四维评分、JD 匹配
├── evaluate.py        RAG 效果评测（LLM-as-judge）
├── build_db.py        早期命令行建库脚本（已不推荐使用）
├── show_db.py         查看库内切分块与向量
├── static/index.html  前端单文件（HTML + CSS + JS）
├── storage/           上传的简历原文与摘要缓存
└── chroma_db/         Chroma 向量库持久化目录
```

## 运行

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

### 2. 配置密钥

在项目根目录创建 `.env`：

```
SILICONFLOW_API_KEY=你的硅基流动密钥
DEEPSEEK_API_KEY=你的 DeepSeek 密钥
```

硅基流动用于 embedding（`BAAI/bge-m3`），DeepSeek 用于生成。

### 3. 启动

```bash
uvicorn main:app --reload --port 8001
```

浏览器打开 `http://127.0.0.1:8001/`。

端口用 8001 是因为 8000 被本地另一个服务占用，可按需修改。

### 4. 使用

打开页面后点左侧「上传简历 (.txt)」，选择文件并填入显示名即可入库。随后可以在右侧直接提问，或点简历条目右侧的 ⓘ 查看概要、全文、评分和 JD 匹配。

> 目前只支持 `.txt` 格式、UTF-8 编码。PDF / Word 支持在后续计划中。

## 已知限制

- **只支持纯文本**：PDF 简历需要先转成 txt；扫描件还需要 OCR
- **无鉴权**：任何人都能上传删除，部署到公网前必须加认证
- **向量库单机**：Chroma 本地持久化，不支持多实例并发写入
- **切分依赖 `[章节]` 格式**：简历如果没有用这种标题，会退化成整篇一块
- **评测未系统化**：`evaluate.py` 有 6 条测试用例，但没有覆盖真实数据集的批量评测
